## Design decisions
1. **No statutory rate exists in code.** Country/employer pay rules (earnings, deductions, brackets, caps, rounding, monthly hours) are DATA, versioned per country+employer, created by one person, approved by another, and immutable once approved (DB trigger). Payroll refuses to run without an approved rule set (`rules_not_approved`). Cameroon (or any country) is just a row. A rule set records the source document it was transcribed from.
2. **Exact decimals only.** `BigDecimal` end to end; rule JSON must supply money/rates as decimal *strings* (JSON numbers are rejected); the browser never converts money to a number. Each line is rounded once with the rule set's mode/scale, totals are sums of rounded lines (a payslip always adds up; a CHECK enforces `net = gross − deductions`).
3. **Maker-checker everywhere, per record and in the database:** staff changes, contracts, rule sets, adjustments, rosters (and overtime), attendance, leave, payroll runs, reversal, payment confirmation.
4. **Payment truth.** An instruction is a request, never a payment. `CONFIRMED` requires a provider reference (single-use), an exactly matching amount and currency, and a confirmer different from the instructor — enforced by a CHECK, so an internal UPDATE cannot "pay" anyone. At most one live instruction per employee and period (partial unique index). Failed instructions can be retried (`-Rn` reference) without ever double-paying. A run becomes `RECONCILED` only when every payable employee is independently confirmed with exact funds.
5. **Locked periods and fingerprints.** Approval locks the period; each run stores a batch hash that is recomputed from the stored lines at approval (tamper → `evidence_mismatch`); calculated results are immutable; run states follow a fixed machine enforced by trigger; reversal is refused once money is confirmed (`reversal_requires_correction`).
6. **Confidentiality.** `CONFIDENTIAL` staff are hidden by a *restrictive RLS policy* unless the verified token carries `m24:confidential_read`; compensation is only returned to `comp_read`/`payroll_read`; amounts never enter audit or outbox events; no raw bank data is stored — only an opaque vault token and a mask (the schema is tested to contain no account-number-like columns).
7. **P03 remains the identity/grant authority.** `staff.user_ref` is an opaque reference; HR records cannot issue privileges. Grants come from the short-lived token claim (≤ 15 min, closed vocabulary).

## NOT verified / honest gaps
* GitHub Actions results for the exact pushed head are recorded on the PR, not here. The Java 27 lane is informational. Next 16.4.5 / React 19.3.1 and a real `next build` were not run (dependency ownership of PRs #23/#24); screens were not rendered in a browser, no responsive or screen-reader check.
* **No real payment-provider or bank integration exists.** Confirmation is manual evidence entry (provider reference, amount, currency, time); there is no webhook/file ingestion, no signature check of provider messages, and no statement import.
* Payroll inputs are simplified: overtime comes from authorised overtime shifts in published rosters; hours for hourly staff from approved attendance; unpaid leave pro-rata by working days; no night/holiday premiums, no mid-period salary changes, no pro-rating for joiners/leavers, no benefits catalogue beyond fixed/percent components, no year-end or statutory-return outputs.
* Leave accrual is whole completed months × rate, capped; no carry-over rules, entitlements by service years, or public-holiday calendars per country.
* No load/performance test; payroll calculation issues several queries per employee (fine for hundreds, needs batching for thousands).
* The `account_token` is stored as supplied; the vault/KMS integration (and field-level encryption where the legal regime requires it) is an external requirement.
* No dependency vulnerability scan or SBOM.

## Remaining external integration / production acceptance blockers
1. Legal/finance owners must supply, transcribe and approve each country's and employer's statutory rules (rates, brackets, caps, contribution bases, rounding) and review the engine against them. None are bundled.
2. P03/identity must issue the `m24:*` grants (including the separation of duties between maker and checker roles) and `confidential_read`.
3. Payment-provider/bank integration with authenticated confirmations; vault for account tokens; retention rules for the idempotency table (it stores full responses).
4. Financial-ledger integration (M-series finance) — M24 does not post to a ledger and must not be treated as the ledger.
5. Data-protection assessment for workforce data; works-council/labour-law review of attendance and leave rules; accessibility audit; penetration test; backup/PITR rehearsal; real OIDC issuer and DBA-provisioned runtime role.
