## Four sequential delivery stages

1. **Engineering implementation batches — 30 at once per execution.** Work through the engineering backlog in **groups of THIRTY substantive, independently implemented and tested batches per requested execution**, never deliberately stop after 1, 5 or 10 and present that as the expected normal quota. The batching boundary is the requested 30-batch run; implementation and GitHub publishing occur **after each individual verified batch** within that run. Finish the defined core/back-end/contract engineering backlog before declaring this stage complete. Do not declare this stage done merely because one group of thirty was published.
2. **Screen production.** After the implementation-batch stage has verifiable closure, systematically implement, bind, and individually verify **all 261 canonical screens**, preserving screen IDs, owner modules, EN/FR, authorized clinical flows, non-glowing accessible design, mobile/desktop responsiveness, and user-approved UI/UX v1.1. Track screen-by-screen source, API integration and real visual/device evidence. Do not equate a mockup or empty screen with implemented.
3. **Module integration and completion.** When the screen inventory stage is complete, integrate and close the **40 canonical modules** end-to-end: workflows, API contracts, persistence, security, roles, offline behavior, inter-module navigation, screens and operational readiness. Track actual per-module exit criteria and blockers. Core domain/API work may already exist from stage 1; this stage completes and validates module integration rather than writing duplicate implementations.
4. **Full audit and formal certification.** Only after screen and module implementation stages are finished, run the dedicated comprehensive code, clinical-safety, security, tenant isolation, performance, accessibility, interoperability, regulatory, deployment and production-readiness audit and qualification programme. Formal certification and external acceptance are **not** performed or claimed as part of earlier development batches. **Mandatory per-batch unit/integration tests, privacy/security invariants, clinical safety constraints and release-denied gates remain active throughout all stages.**

These four stages are an execution workflow **overlay**, not a replacement for the existing **20 programme phases P00–P19**. Do not invent phase-completion percentages or remaining batch counts. Create and reconcile a finite source-backed programme work breakdown (batch and stage exit criteria) before claiming an exact all-platform remaining count.

## Non-negotiable 30-batch execution protocol

- **Before every run and before reserving each batch:** inspect relevant available other SYNQORIA chat context, GitHub `main`, all open PRs and branch heads, `AGENTS.md`, `docs/program/SYNQORIA_MULTI_CHAT_HANDOFF.md`, current batch/phase/module/screen registers, latest available cumulative ZIP/hash, and the source actually on the chosen workstream branch. Never restart work from stale `main` if stacked branches are newer.
- **Assign a coordinated range of 30 unique, phase-qualified batch IDs**, with source-backed descriptions and acceptance tests. Reserve the range visibly and verify there is no conflict; `next_candidate` is not an ownership lock.
- **Execute the 30-batch run in one session**. Each counted batch must contain substantive new source or integration code and its own repeatable focused tests with actual results and evidence. Do not count just a document, stub, unimplemented screen, existing test rerun or renumbering.
- **Immediately after each passing batch, push** source, relevant tests, evidence, and updated ledger as a distinct Git commit on the non-destructive workstream branch. Fetch the remote ref and changed paths to confirm publication before moving to the next batch. Preserve the PR stack; never force-push `main` or overwrite another chat.
- **Cross-chat handoff:** update the shared GitHub handoff and PR discussion with assigned/published range, exact base and head SHAs, actual pass/fail outcomes, remaining work and next *candidate*; this is not proof of a direct message to or read receipt from a separate ChatGPT chat.
- **Failure is not success:** if resource/tool/context/time constraints prevent all 30 from being implemented and verified in this execution, **report the run as incomplete**, give exactly how many were individually tested and remotely published, and distinguish blocked/unpublished work. Do not substitute a normal 1-, 5- or 10-batch cadence. Preserve recovery artifact and SHA-256 where possible; do not fabricate progress, promises of future work, or certification.
- **Accounting and reporting:** separate programme-wide batch totals (not yet reconciled), the historical user's 200-batch request count, number completed/pushed in the CURRENT 30-batch run, current 20-phase status, 261 screens and 40 modules. Include status and stage; do not treat `0 certified` as `0 coded`.
